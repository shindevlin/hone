# BUG 6 Audit — local-state balance mutations that fork state_root

**Pattern (Grouchly's lens):** any code path that reads THIS node's local
chain/block/store state and mutates balances directly, instead of going through the
one quorum-agreed finalization event, forks the balance Merkle root (state_root)
between honest nodes whose local timing differs.

**Method:** `grep store.(credit|debit)` across `rust/hone-node/src/`, then classify each
site by its invocation context: **quorum-ordered** (reached via `apply_entry` /
`validate_and_apply` — the pending-pool → epoch-seal path, deterministic across nodes)
vs **local-timer / API-handler** (runs on wall-clock or a request, per-node — the
defect class).

**Correction (2026-07-16, verified against `f8cbdbacd`).** An earlier revision of this
audit listed **four** defects here and named `session_market::sweep_expired` as one that
"was missed by both sides." That was wrong on two counts, and the line refs (`1292-1305`
/ `1334-1340`) are stale — the call site is now **`main.rs:1453-1456`**. Pin by symbol,
not line: these refs have now rotted twice.

It is **3** balance-mutating defects — `ensemble`, `agent_session`, `vrf`. Those three
are the **same structure as the finalizer bug**: a wall-clock timer calls
`sweep_expired(chain, current_epoch())` and credits based on "expired as of MY local
epoch." Two nodes a fraction of an epoch apart sweep different sets → divergent
balances. NOT yet touched on this branch — flagging for the coordinated fix.

`session_market::sweep_expired` is **not** in that class. It contains no `credit`/`debit`
at all; it only flips `ListingStatus`. Traced: `state_set` writes **`CF_META`**
(`store.rs:216`), while `balance_merkle_root()` — the value the `EpochFinalize` entry
carries (`main.rs:779`) — iterates **`CF_BALANCES`** only (`sorted_balance_entries()`).
Different column families, so its writes cannot enter the balance Merkle root and
**cannot fork `state_root`**. It does still produce a local per-node state divergence
(two nodes disagree on which listings are `Expired`), but that is invisible to consensus
and self-corrects as each node's epoch advances. Contrast `credit()` → `set_balance()` →
`CF_BALANCES` (`store.rs:134`), which is exactly why the other three DO fork.

## The fix template is already in this file — sweepers 5 and 6

Neither this audit's earlier revision nor the sweeper count includes these, and a future
`grep sweep_` that finds six sites with only four classified will re-litigate the whole
question. Both mutate balances; both are **SAFE**:

| Site | Driver | Why it's safe |
|---|---|---|
| `main.rs:1820` `sweep_expired_pending_transfers` | `emit_epoch_rewards(epoch, …)` | receives a **quorum-agreed finalized** epoch |
| `main.rs:1822` `agent_task::sweep_expired` | same | same |

`emit_epoch_rewards` is called from exactly one place — `main.rs:520`, inside the reward
driver's contiguous loop, gated on persisted `epoch_finalized_done:{e}` **and**
`meta["finalized"] == true`. So the same operation (sweep expiries, refund escrow) is
implemented once **correctly** (quorum-driven) and once **incorrectly** (timer-driven,
`main.rs:1453`). The fix for 1/3/4 is to move them onto the path 5/6 already use — not to
invent a mechanism.

Two questions the fix design must answer deliberately (not port mechanically):
1. **Per-epoch idempotency.** `emit_epoch_rewards`'s caller guards with
   `epoch_finalized_done:{e}`. Moving three sweepers behind FinalizedEpoch without an
   equivalent guard risks the double-credit the `ClockReward` comment at `main.rs:2548`
   explicitly warns about.
2. **VRF's offset.** `vrf::sweep_epoch` sweeps `epoch.saturating_sub(REVEAL_WINDOW_EPOCHS)`
   (`=2`, `vrf.rs:23/145`), not `epoch`. Under a finalized-epoch driver that reveal window
   becomes finality-relative rather than wall-clock-relative — a semantic change to the VRF
   game, needing a ruling.

## Likely-SAFE sites (quorum-ordered — reached via apply_entry/validate_and_apply)

These mutate balances but are invoked from the seal-ordered entry-application path, so
every node applies them in the same sha256 order at epoch seal — deterministic:
`agent_session.rs:77/115/119` (apply arms), `agent_task.rs:112/126` (apply arms),
`auction.rs:128/133`, `contracts.rs:200-270` (contract deposit/settle in apply),
`ensemble.rs:66/143/146` (apply arm — but ALSO reachable via the sweep timer above,
so the SWEEP path is the risk, not the apply path), `bridge.rs:91`, `computer_use.rs`.
**Need a second-pass confirmation** that each of these is ONLY reached via apply_entry
and never also from a timer/handler (ensemble is reached from both — its timer path is
the flagged one).

**Note on what "safe" means here (2026-07-16).** Quorum-ordering is one way to be safe;
writing outside the balance Merkle root is another. `balance_merkle_root()` hashes
**`CF_BALANCES`** only, so a mutation that never touches that column family cannot fork
`state_root` regardless of its driver — that's why `session_market::sweep_expired`
(`state_set` → `CF_META`) is off the defect list despite being timer-driven. When
classifying a site, check **both** the driver (timer vs `apply_entry`) and the target
(`credit`/`debit` → `CF_BALANCES` vs `state_set` → `CF_META`).

## API-handler sites (per-request, not consensus — different risk class)

`api.rs:2716-2717` (faucet), `api.rs:7984-8020` (stream inference fees),
`api.rs:8244-8245` (treasury fee). These run on an HTTP request, not consensus — they
mutate local balances directly. On a multi-node chain these MUST become ledger entries
that gossip + seal, or they fork too. Out of scope for the clock-launch fix but on the
same defect list — flag for pre-mainnet review. (`api.rs:2716` faucet is testnet-only.)

## What this branch (`fix/finalizer-determinism`) fixes
1. **Negative attestation:** every elapsed epoch (incl. zero-seal ones) is seeded into
   `epoch_states` so it resolves + finalizes identically on every node.
2. **Recycle + entropy decay moved behind quorum FinalizedEpoch** (deterministic),
   removed from the local finalizer timer; guarded by `epoch_finalized_done:{epoch}`.
3. **Idempotency:** `epoch_finalized_done:{epoch}` gate so a re-fired finalize can't
   double-credit.
4. **Solo bootstrap reward bypass: REMOVED** (updated 2026-07-15, Shin ruling a2d7f6c9:
   ≥2 clocks for rewards). Earlier drafts of this doc said the bypass was *kept/grace-
   scoped* — that is STALE. The bypass is deleted, not grace-scoped: a solo clock seals
   (chain advances) but earns nothing until quorum ≥2 reforms, at genesis or under a
   post-launch partition. A grace counter was the exact pattern that produced the
   permanently-open bypass, so there is no bypass to misconfigure.

## What this branch does NOT fix (needs the coordinated follow-up)
- The **3** balance-mutating sweeper timers (`main.rs:1453/1455/1456`:
  `ensemble::sweep_expired`, `agent_session::sweep_expired`, `vrf::sweep_epoch`) — same
  defect class, not yet moved behind quorum. **This is the next target after convergence
  is proven.** (`session_market::sweep_expired`, `main.rs:1454`, is NOT in this set — see
  the correction above.)
- **The dual `state_root` (found 2026-07-16).** Two different computations share the name:
  the **consensus** value `store.balance_merkle_root()` → the `EpochFinalize` entry
  (`main.rs:779`), and a **proxy stub** `compute_state_root(block_hash, epoch)` =
  `SHA-256(latest_block_hash ‖ epoch)` (`finalize.rs:247`) → the finality snapshot
  (`finalize.rs:69`). The proxy **hashes no state**: two nodes with fully divergent
  balances emit an identical value at the same epoch/block-hash.
  **The go-live gates are safe** — `/api/chain/state_root` (`api.rs:5769`) reads the real
  Merkle root and is the only `/api/*` route exposing one; the runbook's decisive V3 check
  (`docs/FOUNDER_CLOCK_LAUNCH_RUNBOOK.md:143-151`) curls exactly it. So
  `DRYRUN_2CLOCK_2026-07-12`'s `state_root A ≠ B` was a **true negative**, correctly
  catching real divergence.
  **The one proxy consumer is the problem:** `cross_chain_finality.rs:78-91` reads it from
  the snapshot into `compute_announcement_hash` for the **signed `CrossChainAnnouncement`
  published to other chains and inscribed on-chain**. HONE's external proof-of-state is
  therefore a hash of no state, and cannot fail. Scoped fix (unimplemented): repoint
  `finalize.rs:69` at `balance_merkle_root()` — the comment at `finalize.rs:66` invites
  exactly this ("A full Merkle root over all balances can replace this once `scan_all` is
  available"; it now exists and works). Flag-day risk + on-chain entry type +
  outward-facing → needs design review and likely Shin. `latest_finality()` (`store.rs:87`)
  returns the finality **epoch**, not a root — harmless.
- API-handler direct mutations (faucet/stream-fee/treasury) — pre-mainnet review.
