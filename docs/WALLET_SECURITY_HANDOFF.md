# BTCPC Wallet Security Handoff

Date: 2026-04-20

## Current Goal

Wallet creation must be safe for end users and consistent across website, Telegram, API routes, and installer flows.

The custody model is:

- Owner key: rotates keys and controls top-level account authority.
- Active key: moves tokens and authorizes staking.
- Posting key: runs mining nodes and signs operational proofs. Mining machines should only receive this key.
- Memo key: reserved for encrypted memo/message use. No full product surface is assigned yet.

Starter faucet value must never be sellable. Faucet issuance should be delegated BTCPC for inference only, not wallet balance.

## Implemented In This Pass

### Canonical Account Creation

Added `src/services/accountCreation.js`.

All account creation should route through `createAccountForUser()` so the project does not keep drifting between incompatible account payloads.

The service:

- Generates a BIP-39 mnemonic.
- Derives BTCPC owner/active/posting/memo public and private keys.
- Derives EVM, Solana, TON, Bitcoin wallets from the same mnemonic.
- Builds a single copy/paste wallet export block.
- Writes only non-private account data to `secretStore`.
- Records `ACCOUNT_CREATE` with the correct ledger argument shape:
  `recordAccountCreate(username, publicKeys, chainAddresses, epoch)`.
- Issues starter faucet value through `recordDelegate("btcpc_faucet", username, amount, "faucet", epoch)`.

### Secret Store

It also accepts a `public_keys` object for compatibility.

### Staking Authorization

`src/controllers/stakingController.js` now requires an active-key signature for:

- stake
- unstake
- withdraw

Expected challenge strings are generated by `activeKeyChallenge(action, username, amount)`.

Examples:

- `BTCPC_STAKE:stake:alice:1000`
- `BTCPC_STAKE:unstake:alice:`
- `BTCPC_STAKE:withdraw:alice:`

The server verifies `active_signature` against the active public key registered on-chain.

### Reserved Names / Name Assets

Shin's premium-name inventory should not be native top-level accounts at rest.

Implemented model:

- Reserved names live as nested wallets under `shindevlin`, for example `shindevlin/bob`.
- The reserved inventory includes `data/reserved-names.json` plus every lowercase one-, two-, and three-letter combination.
- A user creates an active wallet/account first, receives one mnemonic, and keeps one owner keyset.
- BTCPC HQ can assign a reserved name as a transferable alias to that account, for example `joshua -> josh`.
- Transfers to either `josh` or `joshua` resolve to the same canonical account.
- Aliases are transferable name assets controlled by the current account owner's owner key.

Mnemonic rule:

- The mnemonic belongs to the wallet/keyset.
- Names are assets attached to the wallet.
- Transferring a name asset transfers the name only; it never transfers the mnemonic or private keys.

Primary-name rule:

- A canonical account name such as `josh` is still the account identity.
- Extra names such as `joshua` are aliases/name assets.
- Longer-term, the cleanest model is to make every public name NFT-like and have wallets hold names, with one marked primary.

## Security Notes

- Mining nodes should only have `BTCPC_POSTING_KEY`.
- Owner and active keys should not be written to node `.env` files.
- Faucet value must be delegated, not transferred.
- Mnemonic and private keys are shown once and should not be persisted by the server.
- `secretStore` stores password hashes and public keys, not mnemonic or private role keys.
