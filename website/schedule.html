How Calibration Works

At each era boundary the chain reads the current wall-clock and re-derives all remaining era durations so the total remaining supply exhausts precisely at Bitcoin's projected end timestamp. No governance. No voting. Automatic.

remaining_ms = btc_end_ms − now_ms
series_sum   = 2remaining_eras − 1     // geometric sum: 1 + 2 + 4 + … + 2r−1
base_epoch   = remaining_ms ÷ (4,200,000 × series_sum)

// Stored as chain_param:era_epoch_ms:N for N = current_era … 4
// era N → base_epoch
// era N+1 → base_epoch × 2
// era N+2 → base_epoch × 4 … etc.

BTC Oracle Layer — No Governance Required

Automatic alignment. No voting. No coordination.

Any HONE node running a Bitcoin full node can submit BtcHeightReport entries. The chain maintains a 7-entry rolling median and stores the refined end timestamp in chain_param:btc_end_ms. Era calibration reads this value automatically.

  • Signed by an active clock-node posting key (already a trusted role)
  • Height must be monotonically increasing — no rewinding permitted
  • Implied block rate must be within ±10% of 10 min (540–660 s)
  • Reports older than 720 epochs (~6 h at era 0) are ignored
  • All nodes benefit — even those not running a Bitcoin node

Precision grows each decade. By era 4 (2081) Bitcoin's actual schedule is known to within weeks, so HONE's final calibration lands within ±1 epoch (~7 min) of BTC's last coin.

Idealized vs Calibrated

Without calibration the chain would end ~2150 (124 years). Calibration compresses eras 1–4 by ~10 years so supply exhaustion matches Bitcoin exactly.
